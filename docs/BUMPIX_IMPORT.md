# Перенос Bumpix в joga-crm: серверный импортёр

Команда запускается **на сервере с кодом CRM**, из каталога `back` или внутри
контейнера `api`. Она читает уже скачанные архивы. Логин, Cookie, доступ к Bumpix
и соединение с его сервером ей не нужны.

## Что переносится

- Карточка клиента с исходным Bumpix ID, именем и подтверждёнными по формату контактами.
- Полный исходный профиль: второй телефон, адрес, день рождения, баланс,
  скидка, категории и дополнительные поля сохраняются без потери в JSON.
- Комментарий профиля становится отдельной заметкой CRM. Комментарий записи
  остаётся у соответствующей записи.
- Все выгруженные записи, исходные категории «новые / завершённые / отменённые»,
  история, услуги, мастер, время, доход, расход, напоминания и неизвестные поля.
- Фото каждой записи привязаны к её исходному ID. Аватар хранится отдельно.
- Справочники Bumpix и все версии импортированных снимков сохраняются в базе.

История хранится в таблицах `bumpix_*`, рядом с обычными карточками клиентов.
Время сохраняется как локальная календарная дата и минуты из Bumpix;
часовой пояс не угадывается. Статус фиксируется по выгрузке. «Завершена» в
Bumpix означает, что время записи прошло; это не доказательство оплаты или
фактического посещения. Импорт не запускает уведомления, кассу, списание
абонементов или автоматическое завершение обычных занятий CRM.

**Интерфейс готов:** в карточке клиента появляется вкладка Bumpix с фильтрами,
постраничной историей, мастером, услугами, комментариями и фотографиями.
Во вкладке Профиль доступен исходный профиль; аватар открывается в просмотре.
Фотографии загружаются через защищённые API с авторизацией, а не публичными ссылками. Будущие записи подключаются к обычному журналу отдельной командой
`import_bumpix_journal` после сопоставления услуг и проверки конфликтов (ниже).
Вся сохранённая история уже видна в журнале как исходные карточки Bumpix.
Неподтверждённые отдельные разделы Bumpix, отсутствующие в выгрузке, импортёр
получить не может: он проверяет полноту именно предоставленного архива.

## 1. Подготовить файлы и резервную копию

Дождитесь окончания полной выгрузки. В папке `export/packages` должны лежать
`all-clients.index.json` с `complete: true` и все ZIP, перечисленные в нём.
Нельзя копировать только CSV: в ZIP есть JSON, фото и контрольные суммы.

Поддерживаются три входа:

1. ZIP одного клиента `client-<id>-<snapshot>.zip` — для первого теста.
2. Каталог `packages` со всеми клиентскими ZIP и индексом.
3. Один переносимый ZIP, в корне которого `all-clients.index.json` и все
   перечисленные клиентские ZIP. Архив собирает `C:\Projects\bumpix\code\run-pack.ps1`.

Абсолютные Windows-пути из индекса не мешают: используется только имя ZIP,
а файлы ищутся внутри указанного каталога/архива. Смешивание разных аккаунтов,
дубликаты исходных ID, отсутствие файлов или контрольных сумм останавливают импорт.

Перенесите файлы по SFTP/SCP в закрытую папку сервера. В Docker копируйте
в persistent `uploads`, например `/app/uploads/bumpix/incoming/packages`.
Не помещайте клиентские архивы в публичный `static` или репозиторий.

До обновления схемы и первого импорта сделайте резервную копию PostgreSQL и
**обоих томов: `uploads_data` и `static_data`**. `backup.sh` проекта сохраняет
базу, но сам по себе не сохраняет фотографии. Проверяйте доступность копий.
Откат полного импорта — восстановление этих копий в согласованное окно без
новых изменений пользователей; автоматическое удаление реальных клиентов не выполняется.

## 2. Установить код и обновить схему

Обновите backend из локального проекта, включая обе Bumpix-миграции
`b96d3210e4a7_bumpix_import_history.py` и `d7318c02f4a6_bumpix_journal.py`,
регистрацию моделей/роутеров и `requirements.txt`. Первая продолжает
`c8b73b25dbaf`. Новая миграция журнала продолжает актуальную миграцию проекта
`68dd2348ca56` (она продолжает `b96d3210e4a7`), сохраняя единую цепочку.

На 04.10.2026 проверенная вершина проекта — `d7318c02f4a6`. Перед применением
проверьте `alembic heads` на сервере и используйте **полный актуальный каталог
миграций проекта**, включая `68dd2348ca56`. Команда **`upgrade heads`** ниже
применяет все необходимые зависимости и также работает при нескольких ветках.

На сервере из корня приложения, если используется Docker Compose:

```bash
docker compose exec -T api alembic upgrade heads
```

Без Docker из `back` с активированным серверным виртуальным окружением:

```bash
python -m alembic upgrade heads
```

Не запускайте `--apply` на ноутбуке с рабочим `.env`, пока не проверена целевая
база. Тесты импортёра используют собственную временную SQLite и не читают `.env`.
Новый импортёр использует SQLAlchemy, Alembic, FastAPI и Pillow; версия Pillow
теперь указана явно в `requirements.txt`. При Docker обновите образ обычным
процессом проекта; без Docker установите актуальный `requirements.txt` в venv.

## 3. Проверить архив без базы

```bash
docker compose exec -T api python -m scripts.import_bumpix \
  --input /app/uploads/bumpix/incoming/packages \
  --verify-only --report /app/uploads/bumpix/reports/verify.json
```

Проверяются каждый архив, все SHA-256, совпадение частей JSON, количество
клиентов/записей/фото, принадлежность фото и записей, оригинальная структура
категорий и формат изображений. Проверка не подключается к базе.

## 4. Предпросмотр первых двух клиентов

Замените `42` на ID нужной студии, а `owner@example.com` на email её действующего
владельца. Эти значения не берутся автоматически из первого попавшегося аккаунта.

```bash
docker compose exec -T api python -m scripts.import_bumpix \
  --input /app/uploads/bumpix/incoming/packages \
  --studio-id 42 --owner-email owner@example.com \
  --limit 2 --report /app/uploads/bumpix/reports/preview-two.json
```

Без `--apply` база и клиентские фотографии не изменяются; записывается только
отчёт. В нём:

- `ready`: можно ли импортировать выбранную партию;
- `account_key`: точная подпись исходного аккаунта, нужна для записи;
- `items`: имя, исходный ID, действие `create / link / update / skip / conflict`;
- `candidates` и `candidate_details`: возможные существующие карточки;
- `errors` / `warnings`: что требует решения или осталось в исходном профиле;
- `masters` и `target_team`: исходные мастера и IDs пользователей CRM для сопоставления.

Отчёт содержит имена клиентов, храните его закрыто. `ready: false` означает,
что партия ещё не записывалась. На полном импорте ошибка предпросмотра
останавливает всю партию до первой записи.

## 5. Сопоставить реальные карточки и мастеров

Если в CRM уже есть люди с совпадающим телефоном, почтой или именем, импортёр
не объединяет их автоматически. Создайте на сервере `mapping.json`, например:

```json
{
  "clients": {
    "1.100": 123,
    "1.101": "create"
  },
  "masters": {
    "1.1": 7,
    "1.2": 11
  }
}
```

`123` — ID существующей карточки **в этой студии**. При `link` её профиль,
настройки и реальные данные сохраняются; добавляются связь с Bumpix,
история и исходная заметка. `"create"` — явное решение создать отдельную
карточку даже при совпадениях. Это нужно, например, для двух разных людей
с общим семейным телефоном. Используйте только после проверки кандидатов.

`7` и `11` в `masters` — **`User.id`, не ID строки StudioMember**. Человек должен
быть действующим участником этой студии. Несколько исходных клиентов нельзя
привязать к одной карточке CRM. Уже установленную привязку клиента нельзя
тихо поменять. Указывайте в mapping только исходные ID выбранной партии.

Без сопоставления мастеров сохраняются их Bumpix ID и справочники; владелец
видит историю, но тренер не получает доступ по совпадению имени. Сопоставление
можно добавить позже повторным запуском; оно сохраняется между партиями.
У двух мастеров одного клиента записи остаются отдельными по мастеру.
Явное изменение соответствия мастера применяется ко всем уже импортированным
записям этого мастера в данном аккаунте Bumpix и данной студии, даже если
выбрана одна карточка. Это сохраняет единое соответствие и права доступа.

Повторите предпросмотр, добавив `--mapping /app/uploads/bumpix/mapping.json`.
В первой тестовой партии удобнее использовать конкретные IDs вместо `--limit`:
`--client-ids 1.10 1.100`.

## 6. Записать проверенную партию

Подставьте полный `account_key` из отчёта; короткое имя аккаунта не подходит.

```bash
docker compose exec -T api python -m scripts.import_bumpix \
  --input /app/uploads/bumpix/incoming/packages \
  --studio-id 42 --owner-email owner@example.com \
  --client-ids 1.10 1.100 \
  --mapping /app/uploads/bumpix/mapping.json \
  --account-key ACCOUNT_KEY_FROM_PREVIEW --apply \
  --report /app/uploads/bumpix/reports/import-two.json
```

Без mapping опустите соответствующий параметр. Успех: код завершения `0`,
`complete: true`, для каждой карточки `committed: true`. Прогресс печатает только
исходные IDs и действия. Код `1` — конфликт/ошибка; `130` — ручное прерывание.

Для всей базы уберите `--client-ids`/`--limit`, сначала проведите полный
предпросмотр с mapping для всей партии, затем выполните такую же команду с
`--apply` и `--account-key`. При выборе части данных сначала всё равно
проверяется целостность всего входа: повреждения не замалчиваются.

## Повторный запуск, обновления и фото

Ключ карточки: `(studio_id, account_key, source_client_id)`, ID остаются строками:
`1.10` и `1.100` — разные люди. У записей и фотографий свои уникальные ключи.
Файлы хранятся по SHA-256 в persistent `uploads/bumpix/<studio>/<account>/media`.
Одинаковые байты могут физически храниться один раз, при этом каждая логическая
фотография сохраняет свою связь с клиентом/записью.

При том же снимке действие `skip`: второй клиент или заметка не создаются.
Отсутствующее/повреждённое фото восстанавливается из проверенного ZIP.
Изменения пользователя в CRM не сбрасываются.

При новом снимке созданные импортёром поля обновляются, если в CRM они всё
ещё равны прежнему исходному значению. Если одно поле изменили и в CRM, и в
Bumpix по-разному, импорт блокируется с конфликтом. Профиль явно связанной
существующей карточки импортёр не переписывает. Удалённая исходная заметка
также требует решения, не появляется заново без предупреждения.
Если новый контакт/имя совпадает с другой карточкой, нужен явный mapping
на текущий ID этой карточки Bumpix после проверки совпадения. Подтверждённый
в CRM номер не заменяется данными выгрузки: изменение нужно сначала
разрешить через проверку контакта в CRM, иначе импорт остановится.

Предыдущие снимки и версии фото сохраняются. Исчезнувшая из новой выгрузки
запись помечается `is_current: false`, а не уничтожается. Пустая строка в
отдельном поле не стирает неизвестные исходные поля: весь JSON сохранён.

Каждый клиент записывается одной транзакцией. При сбое сохраняются предыдущие
успешные клиенты; клиент, на котором произошла ошибка, откатывается полностью.
Повторите команду: уже записанные IDs не продублируются. До транзакции могут
появиться файлы без строки БД; они приватные, с контрольными суммами и пригодны
для следующего запуска. Автоматически удалять их импортёр не будет.

## API интерфейса

С обычной авторизацией CRM:

- `GET /clients/{client_id}/bumpix` — исходные профили, справочники, счётчики и аватар.
- `GET /clients/{client_id}/bumpix/events?status=all&offset=0&limit=50` — записи.
- `status`: `all` (все сохранённые текущие), `all_source` (исходный t1),
  `new`, `completed`, `canceled`, `history`, `online`.
- `GET /clients/{client_id}/bumpix/media/{media_id}` — байты фото с проверкой прав.

Владелец/администратор видит свою студию. Тренер видит собственные записи
по сопоставленному `teacher_user_id`; чужие фото недоступны. Фотографии не
публикуются через `static`. Для браузерного `<img>` клиент должен получать
фото через авторизованный API как blob; голый URL без JWT не откроется.
`BUMPIX_STORAGE_ROOT` у API должен указывать тот же persistent каталог,
что `--storage-root` у импортёра (по умолчанию `uploads`, в контейнере `/app/uploads`).

## Проверка кода без рабочей базы

Из `back`, с установленными `requirements.txt` и `requirements-dev.txt`:

```bash
python -m unittest discover -s tests -p 'test_bumpix_*.py' -v
```

Тесты создают только временные SQLite и изображения вымышленных клиентов,
проверяют повторные/частичные запуски, связи, конфликтные правки, scoped API,
целостность архивов, миграцию и восстановление файлов. На сервере сначала
проверьте два клиента в тестовой копии PostgreSQL; локальные тесты SQLite
не заменяют проверку окружения сервера и его резервных копий.

## Обновление интерфейса и проверка

Обновите backend с импортёром и frontend из текущего проекта. Для карточки клиента используется миграция `b96d3210e4a7`;
для журнала дополнительно нужна `d7318c02f4a6` (см. раздел ниже). Соберите frontend
обычной командой `cd front && npm run build` и разместите сборку обычным процессом
сервера. Клиентский ZIP загружается отдельно от кода. Новый интерфейс появится
после успешного импорта; загрузки архива на сервер недостаточно.

Проверки интерфейса: `npm run check:bumpix`, `npm run check:bumpix-journal`, `npm run build`, `npm run lint`,
`npm run check:session`, `npm run check:keys`, `npm run check:i18n`,
`npm run check:uimap`. Проверка браузера выполнялась на искусственных карточках,
без импорта в рабочую базу и без доступа к сессии Bumpix.

«Все (Bumpix)» повторяет исходный список t1. «Все сохранённые записи» также
показывает записи, найденные только в исходной истории. Новые, завершённые и
отменённые записи фильтруются по сохранённым группам Bumpix. При закрытии
карточки или смене клиента загрузка фото отменяется, временные URL освобождаются.

Если переносите один общий ZIP, передайте его путь непосредственно в `--input`
во всех командах выше вместо пути `packages`; распаковывать его вручную не нужно.


## Журнал: история и обычные будущие занятия

После основного импорта история сразу видна в журнале за выбранный день/неделю:
исходные статусы, клиент, мастер, услуга, комментарии, фотографии. Кнопка
«Bumpix · … записей за выбранный период» открывает все исходные записи диапазона,
включая время вне сетки 07–22. Завершённая исходная запись не создаёт фиктивное
посещение или денежную операцию в CRM. Фильтры источника остаются также во
вкладке Bumpix клиента.

Чтобы будущие **новые** записи стали обычными рабочими занятиями, после
основного импорта подготовьте **отдельный** `journal-mapping.json`:

```json
{
  "timezone": "Europe/Prague",
  "currency": "CZK",
  "services": {
    "1.22": 17,
    "1.8,1.10,1.2,1.3": 24
  },
  "events": {}
}
```

Это пример структуры, а не реальные ID услуг целевой CRM. `services` —
точный `service_key` из отчёта → ID уже существующей услуги/комплекса CRM.
Исходные ID — строки; порядок состава сохраняется. Для отдельной записи
можно указать `events["3.1869"] = {"service_id": 24}`. Не передавайте этот
файл основному импортёру: его `mapping.json` содержит только `clients/masters`.

Источник и студия должны иметь одну явно подтверждённую IANA-зону и валюту.
Импорт не конвертирует валюты и не округляет дробные суммы. Мастер должен быть
активным специалистом CRM: тренером или владельцем с назначенными услугами.
При необходимости сопоставьте мастеров в основном импорте и повторите его.

Запуск **из `back/` на сервере**, или аналогично внутри контейнера `api`:

```bash
python -m scripts.import_bumpix_journal \
  --studio-id 123 --owner-email owner@example.com \
  --account-key ACCOUNT_KEY_FROM_MAIN_IMPORT_REPORT \
  --mapping /private/bumpix/journal-mapping.json \
  --report /private/bumpix/journal-preview.json
```

По умолчанию — только предпросмотр. В отчёте есть исходные ID клиента/записи,
`service_key`, время, мастер, сумма, действие `create/link/skip/conflict`.
Исправьте все `conflict`. Тот же запуск с `--apply` создаст **в одной транзакции**
обычные занятия на одно место и брони клиентов. Перед записью проверки
повторяются под блокировкой студии. Никаких уведомлений при импорте не отправляется.

Пересечения с реальными занятиями (с учётом снимков зон и буферов), блокировками
мастера и между переносимыми будущими записями блокируют создание. Если занятие
уже создано в CRM, свяжите его явно:
`"events": {"3.1869": {"service_id": 24, "lesson_id": 987}}`.
Подходит только подтверждённое занятие той же студии/клиента/мастера/услуги,
с совпадающим временем и одной подходящей неотменённой бронью.

Рабочую запись можно переносить и отменять обычными средствами журнала. История
Bumpix, включая полный исходный состав услуги и фото, остаётся в её карточке.
Снимок не появляется второй карточкой в сетке. Повторный запуск не создаёт
дубли, не отменяет ручные изменения и не восстанавливает удалённое занятие.
Фото доступны через защищённый API: после переназначения занятия их видит
текущий мастер CRM, а не прежний исходный мастер.

Оплата источником **не подтверждена**. Импорт не создаёт долг, кассу, списание
абонемента или «оплачено». Карточка явно показывает неизвестную оплату; её
нужно сверить отдельно. Это также касается будущего занятия после его начала.
Исторические суммы сохранены в исходных деталях, а финансовые отчёты CRM
показывают только реальные операции CRM. Перенесённые обычные будущие брони
дальше подчиняются обычным правилам посещений и уведомлений CRM.

Если обычное занятие оказалось за пределами сетки, оно доступно над сеткой
в списке «Записи вне сетки», с обычной карточкой редактирования. Для истории
неизвестные мастера показаны в общей колонке Bumpix, а исходное имя — на карточке.

Миграция `d7318c02f4a6` должна быть применена вместе с предыдущей Bumpix-миграцией
до запуска API. Изменённый архив кода нужно накладывать на существующий проект,
а не заменять им весь проект. Данные и фото остаются в прежнем архиве данных.
