Импорт читает уже проверенный ZIP. Повторный вход в Bumpix и скачивание не нужны.
Сначала тестируем студию **14**, владелец **cartoonlvl2@gmail.com**.

## Результат

- Имя, контакты, день рождения, второй телефон, адрес, категории и аватар находятся в обычном профиле. Баланс до переноса и скидка — отдельные поля.
- Комментарий к клиенту — обычная заметка. Невалидные контакты остаются в ней для исправления.
- Каждая запись становится обычным занятием и бронированием: новые, завершённые, отменённые. Услуги создаются/сопоставляются в каталоге.
- Комментарий и фото доступны у занятия. Эти же фотографии есть в датированной заметке клиента и в его событиях.
- Отдельных кнопки профиля и вкладки Bumpix в карточке клиента нет.

Архив: **1056 клиентов, 2949 записей, 2795 фото** (2788 у записей и 7 аватаров).
Реальных дат рождения в нём нет: значения 0/1 означают «не указано». Первые две карточки не имеют записей или фото — проверяем первые пять.

Завершённая запись не доказывает оплату или фактическое посещение. История не создаёт кассовые операции, долги, абонементы или уведомления задним числом. Неизвестные оплата/посещение так и отображаются. Исходные суммы, единицы услуг и напоминания дополнительно сохраняются в закрытых метаданных миграции.

## Обновление кода на сервере

Требуется миграция **f28a6c9041bd** после **d7318c02f4a6**. Перед обновлением нужна актуальная резервная копия БД, uploads и static. Установщик пакета сохраняет старый код отдельно, но это не резервная копия данных.

После установки файлов:

```bash
cd ~/joga-crm &&
docker compose stop worker &&
docker compose build api worker web &&
docker compose up -d api web
```

Посмотрите `docker compose logs --tail=80 api`: API выполняет миграцию перед uvicorn. После успешного старта:

```bash
docker compose exec -T api alembic current &&
docker compose up -d worker
```

## Полный импорт

Уберите `--limit 5`, сначала снова выполните preview с отдельным отчётом.
Проверка пустой тестовой студии обнаружила **8 карточек с совпадающими контактами и 3 пересечения будущих записей у одного мастера**. Сервер также проверит уже существующих реальных клиентов, занятия и блоки занятости.

Решение по неоднозначной карточке задаётся в JSON: `"clients": {"НАСТОЯЩИЙ_ID_ИЗ_ОТЧЕТА": "create"}`. Create сохраняет отдельную исходную карточку при совпадающих контактах. Числовой ID вместо create связывает с существующей карточкой только этой студии. Не подставляйте заглушку. Разные исходные ID не объединяются автоматически. Решения должны относиться к выбранному набору клиентов.

Пересечения времени проверьте до полного применения. Импортёр не пропускает записи и не меняет им время молча. Пока preview содержит конфликт, apply не начинает перенос. Исходный ZIP остаётся целиком.

## Повтор и ручные изменения

Ключ клиента: студия + исходный аккаунт + ID клиента Bumpix. Ключи занятий, заметок, фотографий и услуг стабильны. Повтор дополняет существующие объекты.

Ручные поля сохраняются; одновременно изменённое в обоих источниках поле даёт конфликт. При связывании с существующим клиентом заполняются только пустые поля. Удалённые вручную занятия и заметки не воссоздаются. Старые фото сохраняются для вручную изменённых заметок.

Оплата, долг, абонемент, удержанные коды и ручная отметка посещения защищают запись от отмены/переноса источником в обход обычных операций CRM. Такие случаи сначала решаются в CRM.

Запись атомарна для одного клиента. Конфликт между preview и apply откатывает этого клиента; ранее завершённые остаются. Отчёт показывает `complete: false` и причину. После исправления повторите команду — дубликатов не будет. Фото доступны только авторизованным сотрудникам нужной студии/мастера.
