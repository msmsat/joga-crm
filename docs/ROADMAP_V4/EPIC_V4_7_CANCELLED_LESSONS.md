# Эпик V4-7 — Отменённое занятие: серая карточка, только факты, вне статистики

Цель эпика простыми словами: отмена занятия сейчас честная только в базе.
В журнале отменённая карточка выглядит и ведёт себя как живая: её можно
таскать и растягивать, попап предлагает записать клиента и изменить занятие, а
сводка дня и отчёты считают её наравне с рабочими. Владелец хочет обратного:
отменённое занятие остаётся на своём месте в сетке — но бледным серым
прямоугольником с надписью «Отменено», который нельзя двигать, по клику
показывает четыре факта (что за занятие, тренер, время, зал) и **нигде** не
участвует в подсчётах.

Источник: запрос владельца 25.07.2026 по итогам живого прогона Журнала.

**Важно понимать про старт:**
- **Бэкенд отмены уже готов** (V4-6, задачи 1–3): `cancel_lesson` ставит
  `status = "cancelled"`, каскадом отменяет резервации, пишет `cancel_reason`
  и `clients_notified`, шлёт c3. Ничего из этого не трогаем.
- **Данные до фронта уже доезжают**: `list_lessons` отдаёт отменённые,
  `utils.ts:230-231` кладёт `cancelReason`/`clientsNotified` в `Booking`,
  карточка уже получает класс `.booking-card.cancelled`
  (`BookingCard.tsx:50` — класс идёт из `b.status`). **CSS-правил под этот
  класс просто нет** — отсюда «живой» вид. Половина фазы 1 — дописать почти
  готовое.
- Этот эпик **заменяет задачи 8–9 эпика V4-6** и сужает их: модалку ввода
  причины (задача 8) не делаем — владелец просил обратное, минимум кликов при
  отмене; причину и статус уведомлений в инфо-виде не показываем (только
  4 факта). Поля в API остаются, вывести можно позже. Задачи 6–7 эпика V4-6
  (двойной тост, confirm при правке) остаются за ним, здесь их нет.
- Отложенный cancel с undo-тостом (`startDeferredCancel`, `Journal.tsx:428`)
  и его страховки не трогаем: карточка гаснет оптимистично, «Отменить» в
  тосте возвращает исходный вид сам.
- Конфликт расписания отменённые уже не создают — `_find_schedule_conflict`
  (`lessons.py:284`) их игнорирует. На место отменённого занятия новое
  ставится без ошибок уже сейчас.

**Обозначения сложности:** 🟢 простая · 🟡 средняя · 🔴 сложная, делать внимательно.

## Фаза 1 — Карточка отменённого занятия

### 1. Серая полупрозрачная карточка + «Отменено» · 🟢 · 0:30
**Простыми словами:** отменённое занятие должно быть видно, но сразу читаться
как нерабочее: бледное, серое, с подписью «Отменено» внутри.
**Сейчас:** класс `.cancelled` на карточке есть, правил под него нет — карточка
цветная, поднимается на hover, курсор `grab`.
**Где:** `front/src/pages/dashboard/Journal/Journal.css` (секция 5 «Карточка
записи», образец рядом — `.booking-card.pending`, :332),
`components/ScheduleGrid/BookingCard.tsx`, `front/src/locales/{ru,en}/journal.json`.
**Что конкретно сделать:**
1. `.booking-card.cancelled { filter: grayscale(1); opacity: 0.45; cursor:
   default; }` — **именно `grayscale`, а не подмена цветов**: фон, рамка и
   текст карточки задаются инлайн-стилями от `b.color`
   (`BookingCard.tsx:67-69`), из CSS их иначе не перебить без `!important`.
2. Отключить hover-подъём и `:active`-курсор для отменённой
   (`.booking-card.cancelled:hover { transform: none; box-shadow: none; }`).
3. В `BookingCard` для `status === 'cancelled'` — бейдж внутри карточки:
   маленькая капсула «Отменено» (`t('grid.cancelled')`, новый ключ в обоих
   словарях), поверх/вместо строки `b-meta`. Счётчик мест и прогресс-бар не
   показываем — мест там больше нет.
4. Инлайн `cursor: canEdit ? 'grab' : 'pointer'` (`BookingCard.tsx:70`) для
   отменённой — `pointer` (клик работает, перетаскивание нет).
**⚠️ Подводные камни:** правило `.booking-card { animation: swipe-enter … }`
(`Journal.css:1241`) ссылается на keyframes, которых нет **нигде** в проекте —
правило мёртвое и `opacity` не перебивает; заодно удалить эти 3 строки.
Тёмная тема отдельных правил не требует: `grayscale` + `opacity` работают от
инлайн-цвета, а не от токена.
**Готово, когда:** отменённое занятие в сетке серое и бледное, с подписью
«Отменено», не подпрыгивает под курсором; рабочие карточки выглядят как
раньше.

### 2. Ни перетащить, ни растянуть · 🟢 · 0:20
**Простыми словами:** на отменённую карточку не действуют правила
перетаскивания и изменения размера — она стоит намертво.
**Сейчас:** `onMouseDown` зовёт `initDrag` для любой карточки, а при выделении
рисуются обе ручки resize (`BookingCard.tsx:51-57`, `:109-120`).
**Где:** `components/ScheduleGrid/BookingCard.tsx`.
**Что конкретно сделать:**
1. В `onMouseDown`: `if (b.status === 'cancelled') return;` — до проверки
   `canEdit` (тост «нет прав» здесь не нужен, дело не в правах).
2. Условие рендера ручек resize (`isSelected && !isDragging && canEdit`)
   дополнить `&& b.status !== 'cancelled'`.
3. `onClick` не трогаем — попап открывается (задача 3).
**⚠️ Подводные камни:** guard ставим в `BookingCard`, а не в
`useDragAndDrop` — хук получает уже начатый drag и о статусе не знает; одна
проверка на входе закрывает и move, и оба resize. Раскладку «лесенки»
(`isCascade`) отменённые по-прежнему занимают — так и надо, занятие физически
стоит на своём месте.
**Готово, когда:** отменённую карточку невозможно сдвинуть и растянуть ни
мышью, ни за края; соседние живые карточки таскаются как раньше.

### 3. Попап отменённого: четыре факта, ноль кнопок · 🟡 · 0:40
**Простыми словами:** клик по отменённой карточке показывает только «что за
занятие, тренер, время и зал» — ни кнопок, ни заполненности, ни списка
записанных.
**Сейчас:** открывается обычный попап с «Добавить», «Изменить», «Удалить»,
шкалой заполненности и списком клиентов; бейдж статуса умеет только
«Подтверждено»/«Ожидает» (`BookingPopup.tsx:231-239`).
**Где:** `front/src/pages/dashboard/Journal/components/BookingPopup.tsx`,
`front/src/locales/{ru,en}/journal.json`.
**Что конкретно сделать:**
1. `const isCancelled = popupBooking.status === 'cancelled';`
2. Бейдж в шапке: для отменённого — «Отменено» (`bookingPopup.cancelled`),
   серая заливка (`rgba(26,26,26,0.06)`, текст `var(--muted)`), без галочки.
   Название и время в шапке остаются — это два из четырёх фактов.
3. Тело: при `isCancelled` рендерим только две строки `bp-row` — зал и тренер
   (блоки уже написаны, `:441-451`). Всё остальное (мест занято, шкала
   заполненности, список записанных, режимы правки и добавления клиента) — не
   рендерим.
4. Блок `bp-actions` (`:520`) при `isCancelled` не рендерим целиком.
5. Эффект загрузки записанных (`scheduleApi.getLesson`, `:110-116`) —
   пропускать для отменённого: данные не показываем, запрос не нужен.
**⚠️ Подводные камни:** попап рендерится через `createPortal` и получает
занятие из кэша — оптимистично отменённое (`patchLocalCancelled`) сразу
попадает в инфо-вид, а «Отменить» в undo-тосте возвращает обычный; проверить
оба перехода при открытом попапе. Причину отмены (`cancelReason`) и
«уведомления отправлены» (`clientsNotified`) **намеренно не показываем** —
владелец просил четыре факта; поля остаются в API и типах.
**Готово, когда:** клик по отменённой карточке даёт название, время, зал и
тренера, бейдж «Отменено» и больше ничего; из этого попапа физически нельзя
ничего изменить.

## Фаза 2 — Отменённое занятие не считается

### 4. Сводка дня и правая панель — по живым занятиям · 🟢 · 0:25
**Простыми словами:** «занятий сегодня», «записей клиентов», «средняя
загрузка», счётчики залов, загрузка тренеров и «Ближайшие» не должны учитывать
отменённые. В сетке карточки при этом остаются.
**Сейчас:** `activeBookings = bookings` (`Journal.tsx:186`) — название врёт,
фильтра нет; метрики (`:590-593`) считают всё подряд.
**Где:** `front/src/pages/dashboard/Journal/Journal.tsx`,
`components/RightPanel.tsx`.
**Что конкретно сделать:**
1. В `Journal.tsx` завести `liveBookings = filteredBookings.filter(b =>
   b.status !== 'cancelled')` и считать по нему `totalClasses`,
   `totalClients`, `avgLoad`.
2. `activeBookings` (уходит в правую панель: счётчики залов и загрузка
   тренеров) — отфильтровать от отменённых там же, где он объявлен
   (`:186`); имя наконец станет честным. В `Grid` по-прежнему уходит
   `filteredBookings` — сетка рисует всё.
3. `UpcomingList` («Ближайшие», `RightPanel.tsx:219`) получает
   `filteredBookings` — передать туда `liveBookings`: отменённое занятие не
   «ближайшее».
**⚠️ Подводные камни:** не подменить источник у `Grid` — иначе карточки
исчезнут из сетки, а это ровно то, чего владелец не хочет. Оптимистичная
отмена гасит метрики мгновенно, undo-тост возвращает — отдельного кода не
требует.
**Готово, когда:** отмена занятия сразу уменьшает «занятий сегодня», обнуляет
его вклад в среднюю загрузку и счётчик зала, убирает его из «Ближайших» — а
карточка остаётся серой на своём месте.

### 5. Отчёты и аналитика: отменённые вне выборок · 🟡 · 0:45
**Простыми словами:** во всех отчётах (загрузка, тренеры, услуги, выручка)
отменённое занятие не должно считаться ни занятием, ни вместимостью —
единственное исключение, где оно нужно, это KPI «Отмены».
**Сейчас:** `lesson_conds` — единая воронка условий по занятиям для всех
эндпоинтов аналитики — статус **не фильтрует**; часть запросов дописывает
`Lesson.status != "cancelled"` руками (`utilization.py:102, 137, 191, 256,
329`), остальные считают отменённые наравне с живыми.
**Где:** `back/routers/analytics/_filters.py` (`lesson_conds`, :63),
`utilization.py`, `team.py`, `reports.py`, `overview.py`.
**Что конкретно сделать:**
1. `lesson_conds(f, sid, *, include_cancelled: bool = False)` — по умолчанию
   добавляет `Lesson.status != "cancelled"`. Один guard в общей функции вместо
   правки десятка вызовов.
2. Два вызова, которым отменённые **нужны**, передают
   `include_cancelled=True`:
   - `utilization._cancels` (:71-76) — он и считает отмены; без флага условие
     станет противоречивым и KPI навсегда обнулится;
   - `team._lesson_stats` (:68-113) — ему нужны обе группы; заодно исправить
     `"lessons": len(by_lesson)` на `len(active_lessons)` (сейчас число занятий
     тренера включает отменённые, а заполняемость — уже нет).
3. Два запроса со **своими** списками условий (мимо `lesson_conds`) — дописать
   фильтр руками: `reports._by_trainer` (`lesson_rows`, :300-308) и
   `overview._overfull_lessons` (`conds`, :209-219).
4. Удалить ставшие дублями `Lesson.status != "cancelled"` в `utilization.py`
   (5 мест выше) — условие теперь приходит из `lesson_conds`.
**⚠️ Подводные камни:** проверить, что после правки KPI «Отмены» и колонка
«Отмены» в отчёте по тренерам всё ещё показывают ненулевые числа — это
единственные два места, где отменённые обязаны считаться. Зарплаты
(`finances/salary.py:32`, `_PAID_STATUSES`), публичная запись и расписание
тренера уже фильтруют отменённые — их не трогаем.
**Готово, когда:** отмена занятия за прошедший период уменьшает «число
занятий» и не влияет на среднюю заполняемость в Отчётах; KPI «Отмены» растёт
на единицу.

### 6. Сервер держит правило: ни записи, ни правки отменённого · 🟢 · 0:30
**Простыми словами:** отменённое занятие нельзя ни переносить, ни менять, ни
записать на него клиента — и это должно держаться на сервере, а не только
серой карточкой в интерфейсе.
**Сейчас:** записать клиента на отменённое занятие можно из карточки клиента и
из журнала (никакой проверки статуса), а `PATCH /lessons/{id}` меняет
отменённое занятие как обычное (`update_lesson` пропускает правило времени
только для `cancel_reason`, но статус не смотрит).
**Где:** `back/services/booking_access.py` (`assert_can_book`, :56),
`back/routers/schedule/lessons.py` (`update_lesson`, :380).
**Что конкретно сделать:**
1. В начало `assert_can_book`: `if lesson.status == "cancelled": raise
   HTTPException(400, "Занятие отменено")`. Это общая воронка — через неё идут
   оба пути записи (`clients/profiles.py:866` и
   `schedule/reservations.py:70`); по отдельным роутерам проверку не
   размазывать. Булев `can_book` — та же проверка → `False` (отменённое
   занятие не попадёт в список «кого можно записать»).
2. В `update_lesson`, рядом с существующим блоком правила времени: если
   `lesson.status == "cancelled"` и в теле есть что-то кроме `cancel_reason` —
   400 «Занятие отменено, изменить его нельзя». Фронту делать ничего не надо:
   `detail` уже показывается error-тостом, оптимистичные правки откатываются.
3. Один pytest в `back/tests/` (образец стаба БД — `test_booking_access.py`):
   `assert_can_book` на отменённом занятии → 400; PATCH с одним
   `cancel_reason` по-прежнему проходит.
**⚠️ Подводные камни:** в `test_booking_access.py` фейковые объекты `Lesson`
могут не иметь `status` — проставить в фикстуре, иначе тесты упадут на
`AttributeError`. Прогон тестов бьёт по dev-БД и реальному SMTP
(известная проблема, эпик N-10) — новый тест писать **без** сети и БД, на том
же стабе.
**Готово, когда:** попытка записать клиента на отменённое занятие возвращает
400 из обоих путей; PATCH отменённого занятия отбивается, кроме правки

## Definition of Done эпика

- Отменённое занятие остаётся в сетке, но выглядит нерабочим: серое,
  полупрозрачное, с подписью «Отменено», без hover-подъёма.
- Его нельзя перетащить и растянуть; попап показывает ровно четыре факта
  (занятие, тренер, время, зал) и ни одной кнопки.
- Ни сводка дня, ни правая панель, ни отчёты не считают отменённые занятия;
  единственные исключения — KPI «Отмены» и колонка «Отмены» по тренерам.
- Сервер сам не даёт записать клиента на отменённое занятие и изменить его
  (кроме причины отмены) — правило не держится на одном интерфейсе.
- Новых компонентов и подсистем не появилось: правки внутри `BookingCard`,
  `BookingPopup`, `Journal.tsx`, `RightPanel` и одного общего `lesson_conds`.
- `npm run build && npm run lint` и pytest бэка чистые.
