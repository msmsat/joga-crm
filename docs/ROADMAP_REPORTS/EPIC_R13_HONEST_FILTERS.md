## Матрица применимости (артефакт эпика, идёт в ROADMAP.md)

`L` — фильтруется через `lesson_conds` (все 4 фильтра), `O` — через `op_conds`
(только тренер и услуга: у `Operation` нет зала и филиала), `—` — не
фильтруется физически.

| Вкладка / метрика | Филиал | Зал | Тренер | Услуга |
|---|---|---|---|---|
| Обзор: Выручка, Прибыль, Структура выручки | — | — | O | O |
| Обзор: Посещения, Активные клиенты, Заполняемость | L | L | L | L |
| Обзор: Динамика клиентов → новые | — | — | — | — |
| Обзор: Динамика клиентов → вернувшиеся, потерянные | L | L | L | L |
| Продажи: всё (Operation) | — | — | O | O |
| Клиенты: Вернувшиеся, Потерянные, Retention | L | L | L | L |
| Клиенты: Ценность клиента | — | — | O | O |
| Клиенты: Новые + график «новые» | — | — | — | — |
| Клиенты: сегменты риска и лояльности | — | — | — | — |
| Команда: занятия, заполняемость, отмены, рейтинг | L | L | L | L |
| Команда: выручка, выручка на час | — | — | O | O |
| Расписание: всё (Lesson) | L | L | L | L |

Сегменты не фильтруются осознанно: они приезжают из общих
`SEGMENT_MATCHERS` (`services/loyalty_matching.py`), которые питают ещё и
Лояльность с кампаниями. Их сигнатура `(db, sid)` — фильтры туда добавлять
значит менять контракт Лояльности, а роадмап у нас на одну страницу. Счётчик
сегмента на Клиентах обязан совпадать со счётчиком в Лояльности — это
задокументированный инвариант (`retention.py:3`), ломать его нельзя.

## Backend Architecture

### Задача 1. `back/routers/analytics/retention.py`

Меняется только то, что физически фильтруется. Никаких новых эндпоинтов, схема
ответа не трогается — фронт не переписывается под задачу 1 вообще.

**`_attended_client_ids` (:72)** — единственная точка, через которую вкладка
Клиенты видит посещения. Сейчас собирает id по датам; получает `f` и уходит на
общий `lesson_conds`:

```python
async def _attended_client_ids(f: ReportFilters, sid: int, d_from: date, d_to: date,
                               db: AsyncSession) -> set[int]:
    # Тот же приём, что в overview.py:90: окно периода подменяем, остальные
    # фильтры (зал/тренер/услуга/филиал) берём из f как есть.
    shifted = replace(f, date_from=d_from, date_to=d_to)
    conds = lesson_conds(shifted, sid)
    stmt = (select(Reservation.client_id)
            .join(Lesson, Reservation.lesson_id == Lesson.id)
            .where(*conds, Reservation.status == "attended").distinct())
    if _needs_hall_join(f):          # join Hall только когда фильтр по филиалу — как в overview.py:35
        stmt = stmt.join(Hall, Lesson.hall_id == Hall.id)
    return {cid for (cid,) in (await db.execute(stmt)).all() if cid}
```

Отсюда автоматически становятся честными `returned`, `lost`, `retention_pct` и
`weekly.returned` — все они считаются от этого множества.

**`avg_value` (в `_kpi:87`)** — деньги, значит `op_conds(f, sid)` вместо ручного
диапазона дат: тренер и услуга применяются, филиал и зал — нет (задача 2
подписывает это в UI).

**`new` и `weekly.new`** остаются на `Client.registration_date` без фильтров —
у клиента нет ни зала, ни тренера. Формула одна и та же с фильтрами и без:
условной второй ветки SQL не заводим (иначе одна и та же цифра значит разное в
зависимости от селекта — худший из возможных отчётов).

**Сегменты (`:290`, `:337`)** — без изменений, см. обоснование выше.

Импорты: `dataclasses.replace`, `Hall`, `lesson_conds`, `op_conds`,
`_needs_hall_join` (переезжает из `overview.py:35` в `_filters.py` — им теперь
пользуются два роутера).

## Frontend Architecture

### Задача 2. Пометка охвата — `CardHeading` из R12

Метрике, которую фильтры не берут, честнее сказать об этом на карточке, чем
дать владельцу молча получить цифру по всей студии.

```tsx
// KpiStat: новый опциональный проп
scopeNote?: string;   // «по всей студии» — рендерится мелкой капсулой под значением
```

Показывается **только когда хоть один неприменимый к метрике фильтр активен** —
без фильтров карточка выглядит как сейчас, лишнего шума нет:

- Клиенты → KPI «Новые»: любой из 4 фильтров активен → пометка;
- Клиенты → «Ценность клиента»: активен филиал или зал → пометка;
- Клиенты → блоки сегментов (`CardHeading` риска и лояльности): любой фильтр →
  пометка в заголовке блока;
- Обзор → «Динамика клиентов»: любой фильтр → пометка (внутри карточки
  «новые» не фильтруются, «вернувшиеся/потерянные» фильтруются);
- Продажи → все денежные KPI: активен филиал или зал → пометка;
- Обзор → «Выручка», «Прибыль», «Структура выручки»: то же.

Правило одно и живёт в одном месте:

```tsx
// Reports/hooks/useScopeNote.ts
// Какие фильтры метрика физически не умеет применять → пометка при их активности.
const UNSUPPORTED: Record<string, ('branch'|'hall'|'trainer'|'service')[]> = {
  money:      ['branch', 'hall'],                       // Operation не привязан к залу
  clientBase: ['branch', 'hall', 'trainer', 'service'], // registration_date, сегменты
};
export function useScopeNote(kind: keyof typeof UNSUPPORTED): string | undefined
```

### Задача 3. Тулбар по вкладкам — `ReportsToolbar.tsx` + `constants.ts`

Нерелевантный селект не должен существовать: на Продажах фильтр по залу не
влияет ни на одну цифру вкладки, показывать его — обманывать.

```ts
// constants.ts — что вкладка реально умеет фильтровать (см. матрицу применимости)
export const TAB_FILTERS: Record<Tab, ('branch'|'hall'|'trainer'|'service')[]> = {
  overview: ['branch', 'hall', 'trainer', 'service'],
  sales:    ['trainer', 'service'],          // Operation без зала и филиала
  clients:  ['branch', 'hall', 'trainer', 'service'],  // через посещения
  team:     ['branch', 'hall', 'trainer', 'service'],
  schedule: ['branch', 'hall', 'trainer', 'service'],
};
```

`ReportsToolbar` получает `activeTab` и рендерит только разрешённые селекты.
Ряд фильтров не должен схлопываться в высоту 0 и дёргать страницу — при 2
фильтрах вместо 4 контейнер сохраняет высоту (`minHeight` ряда), это прямое
следствие R10 (борьба с layout shift).

**Смена вкладки со «спрятанным» активным фильтром:** значение из URL **не
чистим** — владелец вернётся на Обзор и увидит свой фильтр целым. На вкладке,
где фильтр не применим, он не показан и на цифры не влияет (бэк его тоже
игнорирует) — расхождения между экраном и данными нет.

## Styling & UI/UX

- Пометка охвата: 10.5px, `var(--text3)`, капсула `rgba(26,26,26,0.05)`,
  `border-radius: 6px`, `padding: 2px 6px`; в KPI — под значением, в
  `CardHeading` — справа от расшифровки.
- Никаких предупреждающих цветов: это уточнение охвата, а не ошибка.
- Полный текст — в `Tooltip` кита: «Фильтры по филиалу и залу к деньгам не
  применяются: операция не привязана к залу».
- Ряд фильтров: фиксированная высота, селекты не «прыгают» при смене вкладки.

## Edge Cases

| Ситуация | Поведение |
|---|---|
| Клиенты + `trainer_id` тренера без занятий в периоде | `returned`/`retention` = 0, «Новые» с пометкой «по всей студии», EmptyTabState **не** показываем (сегменты не нулевые) |
| Фильтр по филиалу без залов | `lesson_conds` даст пустую выборку — нули без 500, ось графика полная (R6) |
| Фильтр выбран на Обзоре → переход на Продажи | Селект зала не показан, значение в URL сохранилось, цифры Продаж от него не зависят |
| Прямая ссылка `?tab=sales&hall_id=3` | Параметр остаётся в URL, на цифры не влияет, селект не рендерится; на Обзоре снова виден |
| Все 4 фильтра активны на Клиентах | Пометка на «Новых», «Ценности клиента» и двух блоках сегментов; KPI «Вернувшиеся»/«Потерянные»/Retention — без пометки, они честно отфильтрованы |
| Сегмент открыт при активном фильтре | Список клиентов — по всей студии (как счётчик), в подзаголовке модалки та же пометка |
| Экспорт CSV при активном фильтре | Выгружаются те же цифры, что на экране, включая нефильтруемые — расхождения экран/файл нет |

## Definition of Done

- На вкладке Клиенты смена тренера/услуги/зала/филиала **меняет** «Вернувшихся»,
  «Потерянных», Retention и график «вернувшиеся» — проверено вручную и тестом.
- Ни одного видимого селекта, который не влияет ни на одну цифру своей вкладки.
- Каждая нефильтруемая метрика при активном фильтре подписана «по всей студии».
- Счётчики сегментов на Клиентах совпадают со счётчиками в Лояльности при любом
  наборе фильтров (инвариант `retention.py:3` цел, тест 3).
- `EPIC_R6_API_DATA.md` задача 5 отмечена выполненной, матрица применимости в
  `ROADMAP.md`.
- `pytest back/tests/test_analytics_clients_report.py` зелёный,
  `npm run build && npm run lint` зелёные.
