## Принцип эпика

Детализация = **уже существующий срез**, показанный по клику. Новый эндпоинт
заводим ровно один раз — там, где среза физически нет (списки
новых/вернувшихся/потерянных за период). Для цифр, детализация которых уже
лежит на той же вкладке (таблица тренеров, тепловая карта, разрезы потерь), клик
ведёт **в неё**: сортирует, скроллит, подсвечивает. Это честная детализация без
пяти новых эндпоинтов.

Пять цифр остаются без клика осознанно, и это фиксируется в коде комментарием:

| Метрика | Почему без клика |
|---|---|
| Клиенты → Retention | Это доля, а не множество: «54%» не разворачивается в список без произвольного выбора числителя |
| Клиенты → Ценность клиента | Средняя по выручке; детализация — вкладка Продажи, уводить туда с Клиентов вредно |
| Команда → Средний рейтинг | Оценки анонимны (`Reservation.rating`), список раскрывает, кто как оценил |
| Продажи → Средний чек | Дробь от двух других KPI, оба кликабельны |
| Расписание → Свободные места | Разворот = «все прошедшие занятия с местами», это ровно `chronic_low` + карта, уже на экране |

## Backend Architecture

### Задача 1 — `back/routers/analytics/retention.py`

Расширяем **существующий** `GET /analytics/clients-report/segment` тремя
ключами. Своих SQL они не приносят: `_kpi` (`:87`) уже вычисляет ровно эти три
множества клиентов — выносим их в переиспользуемую функцию и отдаём как строки.

```python
# retention.py
PERIOD_SEGMENT_KEYS = ["new", "returned", "lost"]

async def _period_matches(key: str, f: ReportFilters, sid: int, db: AsyncSession) -> list[Match]:
    """Те же множества, что стоят за KPI вкладки: new — registration_date в
    периоде, returned — посещал в периоде И до него, lost — посещал в прошлом
    периоде и не пришёл в текущем. Один источник на цифру и на список, иначе
    счётчик и список разъедутся."""
```

- `value` для этих ключей (`_match_value:317`): `new` → число визитов за период,
  `returned` → число визитов за период, `lost` → дней с последнего визита
  (`_days_since`). Подписи колонки во фронте уже маппятся
  (`ClientsTab.tsx:151 VALUE_LABEL_BY_SEGMENT`) — дописываем три ключа.
- Фильтры применяются по матрице R13: `returned`/`lost` — через `lesson_conds`,
  `new` — без фильтров, с пометкой охвата (механизм R13, задача 2).
- Валидация ключа: неизвестный → 400 (как сейчас), список ключей в одном месте
  (`RISK_SEGMENT_KEYS + LOYAL + ["active"] + PERIOD_SEGMENT_KEYS`).
- Тест в `test_analytics_clients_report.py`: `len(segment('returned')) ==
  kpi.returned.value` для всех трёх ключей — сходимость цифры и списка.

Схема ответа — существующая `list[SegmentClientRow]`, фронтовый
`ClientListModal` подходит без изменений.

**Больше бэкенда в этом эпике нет.** Остальные четыре задачи — фронт на готовых
данных.

## Frontend Architecture

### Задача 2. Клиенты

```tsx
<KpiStat label={t('clients.kpi.new')}      onClick={() => openSegment('new')}      … />
<KpiStat label={t('clients.kpi.returned')} onClick={() => openSegment('returned')} … />
<KpiStat label={t('clients.kpi.lost')}     onClick={() => openSegment('lost')}     … />
```

`openSegment` (`:132`) уже умеет всё: проверку на пустоту, Toast «в сегменте нет
клиентов», дедуп повторного клика. Единственная правка — `segmentCount` (`:129`)
сейчас ищет счётчик только среди `risk_segments`/`loyal_segments`; добавляем в
него три KPI-значения, иначе клик по непустому «Вернувшиеся» покажет Toast.

**Фикс бага 7.** `onClick` переезжает с графика на столбцы — только так известно,
по какому `dataKey` кликнули:

```tsx
// Recharts не отдаёт dataKey в onClick графика (CategoricalChartFunc) —
// поэтому обработчик висит на каждом <Bar> и знает свой вид клиентов.
<Bar dataKey="new"      onClick={(_, i) => openWeek(chartData[i], 'new')} … />
<Bar dataKey="returned" onClick={(_, i) => openWeek(chartData[i], 'returned')} … />
```

`openWeek(point, kind)` не открывает модалку при `point[kind] === 0` (нулевой
столбец — не данные). `handleChartClick` на `<BarChart>` удаляется целиком.

### Задача 3. Продажи

`Drilldown` получает вид `period` — те же операции, что стоят за KPI, за весь
период (запрос `financesApi.getOperations` с `type: 'in'` уже собирается в
`:70 drilldownFilters`, `dateRange` по умолчанию = период вкладки: код готов,
нужен лишь вход):

| KPI | Клик |
|---|---|
| Выручка | `DrilldownModal` — все доходные операции периода |
| Число продаж | тот же список (это его длина) |
| Средний чек | без клика (см. таблицу выше) |
| Доля повторных покупок | скролл к таблице продуктов + сортировка по колонке «Доля повторных» |
| % продлений | как сейчас — вкладка Клиенты (`:174`) |

Сортировка `ProductsTable` по внешнему сигналу — тот же приём, что в задаче 4
(проп `sortBy`).

### Задача 4. Команда

Детализация этих KPI — сравнительная таблица под ними; клик её сортирует по
нужной колонке. Локальное состояние сортировки поднимается в проп:

```tsx
// TrainersTable.tsx: было useState<SortKey>('return_rate_pct')
export interface TrainersTableProps {
  trainers: TrainerRow[];
  onRowClick: (row: TrainerRow) => void;
  sortBy?: SortKey;          // внешний сигнал от KPI-клика; клик по th работает как раньше
}
```

`useState` остаётся источником истины (клики по заголовкам не должны спорить с
пропом), синхронизация — `useEffect` на изменение `sortBy` + скролл к таблице.

| KPI | Колонка сортировки |
|---|---|
| Проведено занятий | `lessons` + `DrilldownModal` со списком занятий периода (`scheduleApi.getLessons`, как на Обзоре) |
| Выручка на рабочий час | `revenue` |
| Средняя заполняемость | `fill_pct` |
| Отмены / no-show | `cancels` |
| Средний рейтинг | без клика |

### Задача 5. Расписание

Все пять цифр разворачиваются в блоки, которые уже есть на вкладке —
`useHighlightRow` из R14 (скролл + подсветка 1.2 с):

| KPI | Клик |
|---|---|
| Средняя заполняемость | тепловая карта |
| Свободные места | без клика |
| Отмены | блок «Отмены и неявки», разрез «По времени» (R14) |
| No-show | блок «Отмены и неявки», переключатель на неявки |
| Упущенная выручка | блок «Хронически низкая загрузка» |

### Задача 6. Affordance

Кликабельная цифра должна выглядеть кликабельной, иначе её никто не нажмёт:

- `Card hover` уже включается от `onClick` (`KpiStat.tsx:27`) — этого мало;
- у кликабельного `KpiStat` появляется шеврон 12px справа от значения,
  `opacity: 0.35`, на hover → `0.7` + сдвиг на 2px;
- `role="button"`, `tabIndex={0}`, `onKeyDown` Enter/Space — цифра доступна с
  клавиатуры (правило «accessibility basics» не упрощаем);
- у некликабельных KPI — ничего нового: отсутствие шеврона и есть сигнал.

Таблица «осознанно без клика» едет комментарием над соответствующими
`KpiStat` — чтобы следующий аудит не открывал этот вопрос заново.

## Styling & UI/UX

- Шеврон-affordance: `stroke: var(--text3)`, `strokeWidth: 2.5`, переход
  `0.2s ease`; в тёмной теме — тот же токен.
- Подсветка блока при скролле: `outline: 2px solid #F9A08B`, `outline-offset: 2px`,
  затухание 1.2 с; `prefers-reduced-motion` → подсветка без анимации.
- Скролл — `scrollIntoView({ behavior: 'smooth', block: 'center' })`, при
  `prefers-reduced-motion` → `'auto'`.
- Заголовок модалки всегда содержит и метрику, и период: «Вернувшиеся клиенты ·
  01.07 — 25.07» — иначе непонятно, чей это список.
- `ClientListModal` и `DrilldownModal` не переделываются: только новые входы.

## Edge Cases

| Ситуация | Поведение |
|---|---|
| KPI = 0, клик | Модалка не открывается, Toast «В сегменте нет клиентов» (готовый механизм `:132`) |
| Столбец графика с 0 новых и 5 вернувшимися | Клик по «вернувшимся» работает, по «новым» — no-op (был баг 7) |
| Список сегмента приехал пустым при непустом KPI | Toast + модалка закрывается (поведение R8/R10, `:85`) |
| Клик по «Отмены» до раскатки R14 | KPI остаётся без клика — задача 5 блокируется зависимостью, не деградирует молча |
| Двойной клик по KPI Команды | Второй клик переключает `sortDir` (обычное поведение сортировки) |
| Клик по KPI при активном фильтре | Список приходит под теми же фильтрами (R13), число строк == значению KPI |
| KPI «Новые» + активный фильтр | Список по всей студии, в подзаголовке модалки пометка «по всей студии» (R13) |
| Enter на сфокусированном KPI | То же, что клик мышью |
| Период = 1 день, «Проведено занятий» | `getLessons(date, date)` — тот же запрос, что drilldown Обзора, попадает в кэш Query |
