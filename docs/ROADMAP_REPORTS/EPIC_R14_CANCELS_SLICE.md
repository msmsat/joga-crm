# EPIC R14 — Расписание: отмены и неявки в разрезах

**Цель:** на вкладке Расписание отмены и no-show существуют как два числа в
шапке — и всё. Владелец видит «47 отмен», но не знает, это вечер пятницы, один

времени, услугам и тренерам» — он же самый частый бизнес-вопрос вкладки: «где мы

## Корень проблемы (найдено в коде)

| Симптом | Причина в коде |
|---|---|
| Отмены — только KPI-число | `utilization.py:71 _cancels` — `count(Lesson.id) where status='cancelled'`, результат уходит в `UtilizationKpi.cancels` (`schemas/analytics/reports.py:261`) и больше нигде не используется |
| No-show — только KPI-число | `_filters.py:noshow_cond()` считает активные брони прошедших занятий; в `UtilizationRead` разреза нет |
| В `SlicesCards` четыре блока, отмен среди них нет | `SlicesCards.tsx:120-129` — топ прибыльных, топ заполненных, хронически пустые, залы |
| Данных для разрезов достаточно | `Lesson.start_time` (час), `Lesson.name`/`service_id` (услуга), `Lesson.teacher_id` (тренер) — ничего нового в БД не нужно, только группировки |

---

## Решения по данным (важно для сходимости цифр)

1. **«Отмена» = отменённое занятие** (`Lesson.status='cancelled'`), ровно тот же
   источник, что у KPI «Отмены». Иначе сумма разрезов не сойдётся с числом в
   шапке — а это первое, что владелец проверит.
2. **«Неявка» = активная бронь на прошедшее занятие** (`noshow_cond()`), тот же
   источник, что у KPI «No-show». Разрез по часу/услуге/тренеру берётся с
   занятия брони.
3. Разрезы считаются **в том же периоде и под теми же фильтрами**, что вся
   вкладка (`lesson_conds`, `include_cancelled=True` для отмен).
4. Группировка по услуге — по `Lesson.name` + `service_id`, как уже сделано в
   `_slices` и `_chronic_low` (`Lesson.name` — то, что видит владелец в Журнале);
   `service_id` едет рядом, чтобы клик мог поставить фильтр.
5. Час — `extract('hour', Lesson.start_time)`, как в `_heatmap`/`_chronic_low`.

## Backend Architecture

### Схема — `back/schemas/analytics/reports.py`

```python
class LossSliceRow(BaseSchema):
    key: str            # 'hour:19' | 'service:12' | 'trainer:4' — для клика
    label: str          # «19:00» | «Пилатес» | «Анна Петрова»
    cancels: int
    noshows: int
    lost_spots: int     # места, которые не были проданы из-за отмены/неявки
    ref_id: Optional[int] = None   # service_id / trainer_id для фильтра тулбара


class LossSlices(BaseSchema):
    by_hour: list[LossSliceRow]
    by_service: list[LossSliceRow]
    by_trainer: list[LossSliceRow]


class UtilizationRead(BaseSchema):
    ...
    losses: LossSlices      # новое поле, добавляется в конец
```

Одна строка держит и отмены, и неявки — владелец сравнивает их в одном ряду
(«у Дмитрия мало отмен, зато много неявок» — это другой разговор, чем «много
отмен»), и фронту не нужны два запроса и две сортировки.

### Задача 1–2 — `back/routers/analytics/utilization.py`

```python
async def _losses(f: ReportFilters, sid: int, db: AsyncSession) -> LossSlices:
    """Отмены и неявки в трёх разрезах. Источники ровно те же, что у KPI
    cancels/noshows — суммы разрезов обязаны сходиться с шапкой."""
```

Два запроса, три группировки каждый (`hour`, `name+service_id`,
`teacher_id`) — считаем в одном проходе и раскладываем в питоне, как это уже
делает `_slices` (`by_name`-словарь): три отдельных SQL на разрез не нужны.

- **Отмены:** `lesson_conds(f, sid, include_cancelled=True)` +
  `Lesson.status == 'cancelled'`; `lost_spots = Σ Lesson.total_spots` (отменённое
  занятие потеряло все места).
- **Неявки:** `lesson_conds(f, sid)` + join `Reservation` + `noshow_cond()`;
  `lost_spots = count(Reservation.id)` (каждая неявка — одно место).
- Имя тренера — join `User` по `Lesson.teacher_id` (как в `_slot_lessons`);
  `teacher_id is null` → строка с `label` = «Без тренера», `ref_id = None`.
- Сортировка: `cancels + noshows` по убыванию, `[:TOP_SLICE_LIMIT]`. Строки с
  нулями и по отменам, и по неявкам не отдаём — пустых сигналов не плодим
  (общее решение роадмапа №3).
- `by_hour` отдаётся **только за часы, где что-то потеряно**, полная ось 0–23 не
  нужна: это список, не график.

`_insights` (`:295`) получает одно новое правило поверх готовых данных, без
своего SQL: `loss_hotspot` — «В {label} отменено {cancels} занятий за период»
для верхней строки `by_hour`, если её доля ≥ 30% всех отмен периода; действие —
`open_schedule_hour` (`action_params: {hour}`) через существующий
`useInsightAction`.

### Задача 5 — тест `back/tests/test_analytics_utilization.py`

1. `sum(r.cancels for r in losses.by_hour) == kpi.cancels.value` — и то же для
   `by_service`, `by_trainer` (сходимость с шапкой; главный тест эпика);
2. то же для `noshows`;
3. отменённое занятие без броней попадает в разрезы (по `total_spots`);
4. фильтр `trainer_id` → в `by_trainer` остаётся одна строка;
5. период без потерь → все три списка пусты, 200 (не 500, не null).

## Frontend Architecture

### Задача 3. `tabs/schedule/LossSlices.tsx` (новый)

Блок встаёт **под тепловой картой, перед `SlicesCards`**: сначала «где
переполнено/пусто», потом «где теряем», потом «что прибыльно».

```tsx
type LossDim = 'hour' | 'service' | 'trainer';

<Card padding={24}>
  <CardHeading
    title={t('schedule.losses.title')}              // «Отмены и неявки»
    description={t('descriptions.schedule.losses')} // «Где студия теряет места: занятия отменены или клиент не пришёл»
    formulaKey="losses"
    actions={/* переключатель разреза: По времени / По услугам / По тренерам */}
  />
```

Переключатель — тот же сегмент-контрол, что у метрик графика Обзора
(`OverviewTab.tsx:226`): переиспользуем разметку, новых паттернов не вводим.

Строка разреза — три числа в ряд, отмены персиковым, неявки серым, потерянные
места справа:

```
19:00        отмен 12   неявок 8    −34 места
Пилатес      отмен  9   неявок 3    −21 место
```

Пустой разрез (`by_*.length === 0`) → `EmptyState` кита размера `sm` с текстом
«В этом периоде отмен и неявок не было» — это хорошая новость, а не пустая
таблица (правило R8).

Данные уже приезжают в `getUtilization` — новый запрос **не** нужен, только
поле в `types.ts` (`ScheduleTab` уже держит весь ответ).

### Задача 4. Клик по строке

Разрез — не таблица для чтения, а вход в детализацию:

| Разрез | Клик |
|---|---|
| По тренерам | `setFilter('trainerId', ref_id)` — вся вкладка пересчитывается по этому тренеру |
| По услугам | `setFilter('serviceId', ref_id)`; `ref_id === null` (занятие без услуги) → строка не кликабельна |
| По времени | Скролл к тепловой карте + подсветка строки этого часа на 1.2 с |

Фильтр ставится существующим `setFilter` из `useReportFilters` — новых
механизмов нет; `ScheduleTab` получает `onFilterChange` пропом из `Reports.tsx`
(тулбар уже его имеет).

Подсветка часа — общий хук на эпик R15, здесь заводится минимальная версия:

```tsx
// Reports/hooks/useHighlightRow.ts
// Скролл к блоку и мигание строки: единственная «детализация» там, где
// отдельного списка нет и заводить эндпоинт под него незачем.
export function useHighlightRow(): (blockId: string, rowId?: string) => void
```

`CSV` вкладки Расписание (`ScheduleTab.tsx:43 csvRows`) дополняется строками
разрезов — экспорт обязан отдавать то, что на экране.

## Edge Cases

| Ситуация | Поведение |
|---|---|
| Период без отмен и неявок | Блок рендерится с `EmptyState` «отмен и неявок не было» |
| Занятие отменено, броней не было | Попадает в разрезы, `noshows = 0`, `lost_spots = total_spots` |
| Занятие без тренера (`teacher_id = null`) | Строка «Без тренера», `ref_id = null`, клик не ставит фильтр |
| Занятие без услуги (`service_id = null`) | Группируется по `Lesson.name`, клик не кликабелен |
| Клик по тренеру, у которого фильтр уже стоит | Повторный клик снимает фильтр (toggle) — иначе выхода из среза нет |
| Отменённое занятие вне рабочих часов (03:00) | Час показывается как есть, полная ось не нужна |
| Фильтр по залу + разрез по тренерам | Разрезы считаются под фильтром (`lesson_conds`), сумма сходится с KPI **под тем же фильтром** |
| Период = один день | Разрез по часам осмысленен, по тренерам/услугам — обычно 1–2 строки, это нормально |

- Пустой период показывает EmptyState, а не пустую таблицу.
- CSV Расписания содержит строки разрезов.
- `pytest back/tests/test_analytics_utilization.py` зелёный,
