# Эпик N-9 — Три живых канала для каждой роли + добивка «мёртвых» событий

Цель простыми словами: сейчас **реально три канала (email + Telegram + WhatsApp)
работают только у клиента**. У тренера, админа и владельца доходит **только
email** — Telegram и WhatsApp для них физически не отправляются, сколько галочек
в матрице ни ставь. Плюс 6 событий каталога не стреляют вообще (нет ни шаблона,
ни врезки). Этот эпик закрывает обе дыры: сотрудники получают tg/wa по своим
реквизитам, и каждое событие матрицы получает реальный триггер.

**Важно понимать про старт (что уже проверено по коду, 2026-07-24):**
- Ядро `notify(db, studio_id, role, event_id, context)` живое; врезка = 1 строка.
- Диспетчер каналов `deliver()` и `_send_whatsapp()` уже умеют слать во все три
  канала — но принимают `Client`. Сотрудник не `Client`, поэтому tg/wa мимо.
- `User.phone` **есть** (`models/user.py`) → для WhatsApp сотрудника поле готово.
  `User.tg_id` **нет** → для Telegram сотрудника нужна одна колонка.
- `UserSession` (`models/settings.py:229`) пишет `device/platform/browser` → a9
  «Попытка входа» стала врезаемой (в N-4 была отложена — инфры не было).
- Эндпоинт экспорта есть (`finances/operations.py:115` `/operations/export`) → o9
  врезаема (в N-4 отложена).
- Эндпоинта создания отзыва **нет** (`StudioReview` — только модель + GET-отчёты,
  сам отзыв придёт из клиентского мини-приложения, 2-я очередь) → t7 остаётся в
  BACKLOG, но точка врезки зафиксирована ниже.

**Обозначения сложности:** 🟢 простая · 🟡 средняя · 🔴 сложная, делать внимательно.

## 🎯 Две корневые причины (не симптомы)

**Причина №1 — сотрудники недостижимы в tg/wa (25 событий).**
Один узел: в `notifier.notify()` каналы tg/wa зашиты под `if client is not None`,
а `_recipient()` для ролей trainer/admin/owner возвращает `(None, [emails])` — без
`Client`, значит без `tg_id`/`phone`. Это осознанное MVP-ограничение N-1, теперь
снимаем. Фикс — **в одном месте** (`_recipient` + `notify`), не в 25 врезках.

**Причина №2 — 6 событий без шаблона и без триггера:** t2, t5, t7, a7, a9, o9.
`notify()` для них честно возвращает `False` (нет шаблона). Матрица галочки
сохраняет — но слать нечего.

### 2. Обобщить получателя и снять гейт · 🔴 · 1:30
**Где:** `back/services/notifier.py` — `_recipient()`, `notify()`, `deliver()`.
**Суть:** сегодня `deliver()` завязан на `Client`. Развяжем через лёгкий
получатель — и клиент, и сотрудник пойдут одним путём (это **упрощение**, а не
рост кода: уходит развилка `client is not None`).

```python
# notifier.py
from typing import NamedTuple

class Recipient(NamedTuple):
    id: int | None       # для логов
    email: str | None
    tg_id: int | None
    phone: str | None
```

- `deliver(...)` принимает `recipient: Recipient` вместо `client: Client`
  (обращения `client.email/.tg_id/.phone/.id` совместимы — `Client` тоже подходит
  под этот интерфейс, но явный тип чище). `_send_whatsapp(cfg, recipient, text)`
  читает `recipient.phone`.
- `_recipient()` возвращает `list[Recipient]` для **всех** ролей:
  - `client` → `[Recipient(c.id, c.email, c.tg_id, c.phone)]`;
  - `trainer`/`admin`/`owner` → по строке на сотрудника:
    `Recipient(u.id, u.email, u.tg_id, u.phone)` (те же выборки по `StudioMember`,
    что и сейчас, но тянем ещё `User.tg_id`/`User.phone`, а не только `email`);
  - `context["to_email"]` (точечный адресат, напр. тренер занятия при t3/t6):
    достаём **всю строку** `User` по этому email → `Recipient` с его tg_id/phone,
    а не `(None, [email])`.
- `notify()`: убрать ветку `if client is not None`. Единый цикл:
  ```python
  sent = False
  for r in recipients:
      if "email" in enabled_channels and r.email:
          sent = await deliver(db, "email", r, subject, text, html, studio_id=studio_id) or sent
      if "telegram" in enabled_channels and r.tg_id:
          sent = await deliver(db, "telegram", r, ...) or sent
      if "whatsapp" in enabled_channels and r.phone:
          sent = await deliver(db, "whatsapp", r, ...) or sent
  ```
**⚠️ Подводные камни:**
- Email сейчас шлётся `send_email()` напрямую в цикле, а не через `deliver`.
  Свести к одному пути `deliver(db, "email", r, ...)` — там уже верифицированный
  отправитель студии (`email_sender`). Поведение для клиента не меняется.
- `t3`/`t4`/`t6` передают `to_email` — после правки они **тоже** получат шанс на
  tg/wa (если у тренера привязан chat_id/телефон). Это желаемое поведение.
- Персональный тумблер сотрудника «получать уведомления» (ТЗ 2.4/2.13) — вне
  этого эпика; сейчас матрица владельца = единственный фильтр. Отметить в BACKLOG,
  если всплывёт.
