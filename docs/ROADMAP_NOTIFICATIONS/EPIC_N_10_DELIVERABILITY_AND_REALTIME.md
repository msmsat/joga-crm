# Эпик N-10 — Доставляемость, надёжная рассылка (outbox) и real-time

Цель простыми словами: (1) немедленно остановить поток баунсов «Address not
found» — сейчас **тесты бьют по боевой почте**; (2) сделать так, чтобы письма и
сообщения слались **надёжно и постоянно** — durable outbox + воркер с ретраями,
а не inline-отправка, которая теряется при рестарте; (3) навести порядок в
каналах (согласованность «включён ⇔ подключён», self-check живости); (4) отдельно
— **real-time в UI** (живой фид/колокольчик) через SSE, если он нужен.

> ⚠️ **Терминологическая правка (важно).** В постановке был «внедрить вебсокеты,
> чтобы они постоянно рассылали письма». Технически это два разных механизма:
> **WebSocket/SSE не отправляют письма** — это транспорт браузер↔сервер для
> live-UI. Письма шлёт SMTP, Telegram — Bot API, WhatsApp — Cloud API, всё это
> серверный фоновый воркер. Поэтому «постоянная надёжная рассылка» = **Фаза 3
> (outbox + воркер)**, а «real-time в интерфейсе» = **Фаза 5 (SSE)**. Не путать и
> не решать одно другим.

**Обозначения сложности:** 🟢 простая · 🟡 средняя · 🔴 сложная, делать внимательно.

## Фаза 3 — Надёжная ПОСТОЯННАЯ рассылка (durable outbox + воркер)

> Это и есть «чтобы постоянно рассылали надёжно». Не вебсокеты — очередь.

### 7. Таблица `notification_outbox` + enqueue вместо inline · 🔴 · 2:30
**Где:** новая модель + миграция; `services/notifier.notify()`.
**Что:** `notification_outbox`:
`id, studio_id, role, event_id, channel, recipient_ref (email/tg_id/phone),
payload_json (subject/text/html), status (pending|sent|failed|dead|suppressed),
attempts, next_attempt_at, last_error, dedup_key, created_at, sent_at`.
`notify()` перестаёт слать inline — **резолвит получателей/каналы и кладёт по
строке в outbox** (status=pending), мгновенно возвращает управление. `dedup_key =
hash(studio, role, event, recipient, окно_времени)` — защита от дублей при
повторных тиках/ретраях запроса.
```
# ponytail: одна таблица-очередь вместо брокера (Redis/RabbitMQ) — для одного
# воркера uvicorn этого достаточно; брокер — когда появится второй инстанс.
```
**⚠️:** это меняет контракт `notify()` с «отправил» на «поставил в очередь» —
`clients_notified`/возврат `bool` теперь = «поставлено», а факт доставки узнаём
из outbox. Проверить все места, где по возврату `notify()` строится UI-ответ
(напр. `send_subscription_reminder` в `clients/profiles.py`).

### 8. Воркер-драйнер: ретраи, backoff, dead-letter, suppression · 🔴 · 2:30
**Где:** `services/outbox_worker.py` (образец цикла — `scenario_runner`/`daily_notify`),
старт в `main.py` lifespan.
**Что:** каждые N секунд берёт `pending`/`failed` с `next_attempt_at <= now`,
шлёт через `deliver()`, при успехе → `sent`; при ошибке → `attempts++`,
экспоненциальный backoff (`next_attempt_at`), после `MAX_ATTEMPTS` → `dead`;
адрес из suppression → сразу `suppressed`. Батч + `SELECT … FOR UPDATE SKIP
LOCKED` (или advisory-lock) на будущее для нескольких воркеров.
```
# ponytail: линейный дренаж одной таблицы, backoff арифметикой в next_attempt_at,
# без Celery/APScheduler — как остальные циклы проекта.
```
**⚠️:** воркер не должен зациклиться на «мёртвой» строке (обязателен `dead` после
лимита). `daily_notify`/`scenario_runner` теперь тоже кладут в outbox, а не шлют
сами — иначе два пути доставки.

## Фаза 4 — Real-time в UI (SSE) · опционально

### 9. SSE-эндпоинт живого фида · 🔴 · 2:00
**Где:** `routers/…/stream.py` (`GET /notifications/stream`, `text/event-stream`),
фронт — `EventSource` в сторе уведомлений.
**Что:** сервер пушит в браузер событие «новое уведомление/обновление матрицы»,
UI обновляет фид/колокольчик без F5. Источник — запись в outbox/лог событий.
**Почему SSE, а не WebSocket:** нужен односторонний server→client поток; SSE проще
(обычный HTTP, авто-reconnect, работает на текущем ASGI без отдельного WS-слоя),
совпадает с прежним решением роадмапа «отдельного WS-сервера не заводим».
```
# ponytail: SSE вместо WS — тот же результат для фида, вдвое меньше инфры;
# полноценный WS — только если появится реально двусторонний обмен.
```
**⚠️:** SSE — про **UI**, он не заменяет outbox. Письма/TG/WA всё равно шлёт
воркер (Фаза 3). Не тащить в SSE отправку по каналам.

## Что НЕ делаем (границы, ponytail)
