## R1 — P1: FOR UPDATE возвращает устаревшее состояние Studio

Место: `back/services/schedule_guard.py:41–51`.

Сценарий: сессия B загрузила Studio с `strict_schedule_enabled=false`; сессия A под замком включила strict и закоммитила; B вызывает `lock_studio` и получает объект с прежним `false`. Независимый тест это воспроизвел на PostgreSQL.

Причина: повторный ORM SELECT без `populate_existing`/refresh не обязан перезаписывать уже загруженные атрибуты в identity map. Сам SQL-замок работает; актуальность бизнес-состояния не обеспечена. Поэтому существующий тест двух свежих сессий не доказывает безопасность включения strict.

Исправить:

1. Гарантировать актуальное состояние Studio после получения замка с учетом правил autoflush.
2. Проверить ранее загруженные Lesson/Reservation/Service и другие объекты в затронутых путях: повторный SELECT сам по себе не является гарантией refresh.
3. Захватывать Studio до бизнес-мутаций и дочерних блокировок; не пытаться исправить порядок одним `populate_existing` после уже выполненных изменений.
4. Исправить комментарии, приравнивающие любой повторный SELECT к обновлению ORM-состояния.

Приемка: `test_lock_refreshes_preloaded_studio` проходит; дополнительный конкурентный тест с Events доказывает, что ожидающий запрос после включения strict видит новое значение и отклоняет конфликт. Проверить аналогичный сценарий со сменой условий услуги.
