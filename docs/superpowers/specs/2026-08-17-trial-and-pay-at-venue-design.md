# Пробное занятие и оплата на месте

Дата: 2026-08-17. Статус: реализовано (миграция `c3f81a204b7d`).

## Задача

Две дыры в логике записи, из-за которых мини-приложение не сводится с деньгами:

1. **Пробное занятие.** Студия не может подарить новому клиенту первый визит —
   любая запись либо требует абонемент, либо не оставляет о себе финансового следа.
2. **Оплата на месте.** Записаться без абонемента уже можно (тумблер «Предоплата
   при записи» выключен), но дальше не происходит НИЧЕГО: долг нигде не виден,
   приход клиента не превращается в деньги, отметка посещения про оплату не
   спрашивает. Наличные в кассе есть — в CRM их нет.

Дополнительно: чтобы студия могла позвонить и написать клиенту, оплата на месте
требует телефон. Мини-приложение сегодня телефон не собирает вовсе.

## Решения, принятые до дизайна

| Вопрос | Решение |
|---|---|
| Где тумблер пробного | «Онлайн-запись → Правила записи», рядом с «Предоплата при записи», которую он отменяет |
| Телефон вне Telegram | В браузере вводится руками, без подтверждения; разница фиксируется флагом |
| Клиент не заплатил на месте | Долг создаётся и висит: письмо клиенту, плашка везде, вопрос админу при каждой отметке — пока не погасят |

## Модель данных

Четыре колонки, ни одной новой таблицы.

| Таблица | Колонка | Зачем |
|---|---|---|
| `studio_booking_settings` | `trial_lesson_free` bool, default false | Тумблер студии |
| `reservations` | `is_trial` bool, default false | Эта бронь — подаренное первое занятие |
| `reservations` | `debt_payment_id` int null, FK → `client_payments.id` ON DELETE SET NULL | Долг за эту бронь |
| `clients` | `phone_verified` bool, default false | Номер подтверждён Telegram, а не введён руками |

**Долг — это `ClientPayment(status='pending')`**, а не новая сущность:
`action_type='lesson'`, `item_key=str(lesson_id)`, `amount=lesson.price`.
Обоснование — модель уже допускает `pending` в CheckConstraint, карточка клиента
читает только `status='success'` (`routers/clients/profiles.py:549`, существующие
экраны не поедут), а мини-приложение отдаёт историю платежей без фильтра по
статусу — клиент увидит «не оплачено» без единой правки `/me/payments`.
Отдельная таблица `ClientDebt` означала бы две ленты истории в мини-приложении и
переходник, чтобы погашение прошло через денежный движок.

**`debt_payment_id` на брони, а не `reservation_id` на платеже**: при включённой
«Повторной записи» у клиента бывает две брони на одно занятие, и по паре
`client+lesson` долги не различаются. Плюс `ClientPayment` — общая модель
(абонементы, разовые), и поле, нужное одному сценарию, ей не место.

## Где живёт логика

Все три пути записи (Журнал `routers/schedule/reservations.py`, мини-приложение
`routers/booking/miniapp_lessons.py`, веб-виджет `routers/booking/public.py`)
уже сходятся в `services/subscription_charge.charge_reservation` — туда и
врезается долг, одним куском на всех. Отмена во всех трёх путях идёт через
`refund_reservation` — там долг снимается. Разъехаться копиям физически негде.

Функции (в `services/subscription_charge.py`, рядом со списанием абонемента —
это тот же вопрос «чем оплачена эта бронь»):

- `trial_applies(db, studio_id, client_id, rules) -> bool` — тумблер включён И у
  клиента нет ни одной неотменённой брони.
- `open_debt(db, reservation, lesson) -> ClientPayment | None` — зовётся из
  `charge_reservation`, когда абонемент не подобран и бронь не пробная.
- `clear_debt(db, reservation)` — зовётся из `refund_reservation`; удаляет
  pending-строку. Погашенный (`success`) долг не трогает никогда.

## Фаза 1. Пробное занятие

Право на пробное: `rules.trial_lesson_free` И у клиента нет неотменённых броней
(один `SELECT ... LIMIT 1`). Пробное выдаётся только тому, у кого нет
подходящего абонемента: купил — значит уже не пробует.

Сработало → `Reservation.is_trial = True`, гейт `prefill_on_booking` пропускается
(абонемент не требуется), долг не создаётся, абонемент не списывается.

Принятые грани поведения:
- забронировал два занятия вперёд — пробное только первое (вторая бронь видит
  первую неотменённую);
- отменил пробную бронь до визита — пробное вернётся (визита не было).

Поверхности: тумблер в `BookingSettings.tsx`; бейдж «Пробное» в строке
записанного клиента в Журнале; в мини-приложении кнопка записи говорит
«Бесплатно · пробное занятие» вместо цены.

## Фаза 2. Телефон

`POST /global/me/phone`:
- **из Telegram** — `tg.requestContact()` отдаёт подписанный ботом ответ; подпись
  проверяется тем же `verify_init_data`, что и вход в мини-приложение (схема
  подписи у них одна). `phone_verified = True`;
- **из браузера** — ручной ввод, валидация схемой `Phone` (E.164, уже есть в
  `schemas/_base.py`), `phone_verified = False`.

SMS-шлюза в продукте нет и не заводим: Telegram подтверждает номер сам, бесплатно
и без OTP-флоу.

Поверхности: шит «Оставьте номер» в мини-приложении; в карточке клиента CRM —
отметка у подтверждённого номера, чтобы админ знал, дозвонится ли гарантированно.

## Фаза 3. Долг и оплата на месте

**Возникновение.** Бронь без абонемента и не пробная → `open_debt` создаёт
pending-строку на `lesson.price` и кладёт ссылку в `reservation.debt_payment_id`.

Долг заводят только ОНЛАЙН-пути (мини-приложение, веб-виджет) — там запись без
абонемента возможна уже сегодня. Журнал и карточка клиента сохраняют свой гейт
`assert_can_book`: администратор по-прежнему сначала продаёт через кассу. Менять
это правило заодно значило бы переписывать офлайн-продажу, которой никто не
просил. Пробное занятие, наоборот, снимает гейт во всех четырёх точках: подарок
не должен зависеть от того, какую кнопку нажал администратор.

**Гейт телефона.** Запись, которая создаёт долг, без `client.phone` → **428**;
мини-приложение по этому коду открывает шит с номером. Веб-виджет телефон
собирает формой и под гейт не попадает.

**Созревание.** Отметка посещения (`PATCH /schedule/reservations/{id}/attend`)
на брони с непогашенным долгом шлёт клиенту новое событие **`c10` «Занятие не
оплачено»** (`client` / `critical` / email — по образцу `c9` «возврат средств»:
деньги, место в почте).

**Погашение.** `POST /schedule/reservations/{id}/pay` (владелец и админ; тренер
деньги не берёт) зовёт существующий `perform_pay` из `routers/checkout/router.py`
с новым `product_type="lesson"`. Способы — `cash` и `transfer`: «card» в кассе
означает эквайринг Stripe и проводится вебхуком после реального списания, а не
нажатием кнопки, — терминал студии как и раньше идёт через кассу. Оттуда бесплатно приезжает всё, что уже
написано: доход в Финансы, комиссия платформы за офлайн (`record_offline_fee`),
баллы, `register_purchase`, событие `c4` «оплата получена», запись в Событиях.

Правки в `checkout/router.py`:
- `ProductType` += `"lesson"`; `_get_client_package` резолвит `Lesson` в
  `ServiceAsProduct`;
- `ServiceAsProduct` получает отдельное поле `service_id: int | None` — сейчас
  `Operation.service_id` берёт `package.id`, а у занятия услуги может не быть;
- `perform_pay` получает необязательный `debt: ClientPayment | None`: передан —
  обновляет его до `success` вместо создания второй строки.

**«Спрашиваем, пока не нажмёт да».** Клик «Отметить посещение» на брони с долгом
спрашивает: «Клиент оплатил? Наличными / Картой / Ещё нет». «Ещё нет» —
посещение отмечается, красная плашка «Не оплачено · N» с кнопкой «Оплатить»
остаётся в Журнале до погашения. Тренер отмечает посещение как раньше: вопрос про
деньги показывается только владельцу и админу.

**«Везде показываем».** Журнал — плашка в строке записанного; карточка клиента —
бейдж «Долг · N»; мини-приложение — «Не оплачено» на карточке занятия и
pending-строка в истории платежей.

## Что НЕ делаем

- Частичное погашение долга (оплатил половину наличными) — гасится целиком.
- Долг за пропущенное занятие (записался, не пришёл, не отменил): долг создан,
  но `c10` уходит только при отметке посещения. Списывать деньги за no-show —
  отдельное решение студии, которого никто не просил.
- Автонапоминания о долге по расписанию: письмо одно, дальше долг живёт на
  экранах. Строку «неоплаченных занятий: N» в дневной отчёт `a8` — если попросят.
- Пробное на конкретную услугу/направление: тумблер один на студию.
